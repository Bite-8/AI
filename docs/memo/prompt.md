# 自立開発ワークフロー

このリポジトリを、`GOAL.md` のゴールへ継続的に近づける。

このプロンプトは定期実行される。各実行ではGitHubとリポジトリの最新状態から現在の工程を判定し、以下の優先順位に従って、最初に該当する作業を1つだけ完了して終了する。

## Human gate

次の2回のHuman確認を必須とし、エージェントの判断で省略しない。

1. **Issue確認**: エージェントが提案した作業内容が、現在の状態からゴールへ進む作業として妥当かHumanが確認する。承認されるまで実装しない。
2. **PR確認**: 実装内容がIssueを適切に実現しているかHumanが確認する。エージェントはmergeしない。

Human承認者はGitHubユーザー `bara8383` とする。

- Issueの実装承認は、`bara8383` による `/approve-issue` コメントを原則とする。既存Issueについては、「実装してよい」など実装許可が明確な過去コメントも有効とする。
- bot自身のコメント、レビュー、reaction、labelはHuman承認として扱わない。
- Issueの目的、スコープ、完了条件を承認後に実質的に変更した場合、以前の承認は無効とし、再承認を待つ。
- PRの承認は、`bara8383` が最新のhead commitに対して行ったGitHubのApprove reviewだけを有効とする。
- エージェントはPRをmergeせず、Humanによるmergeを待つ。

## 毎回最初に行う確認

1. ルートの `GOAL.md` と `AGENTS.md` を読む。
2. リポジトリの構成、関連する実装とドキュメント、現在のbranch、作業ツリーの状態を確認する。
3. remoteをfetchし、localとremoteの差分を確認する。
4. open中のIssueとPR、および全コメント、review、最新head commit、CI結果を確認する。
5. 同じIssueに対応するopen PRや、同じ目的のIssueが既に存在しないか確認する。

作業ツリーに未保存の変更がある、remoteとの安全な同期ができない、競合がある、認証や権限が不足している場合は、既存状態を上書きせず、その理由を報告して終了する。

## 作業の選択順序

### 1. open PRに未対応のフィードバックがある

エージェントが作成したopen PRに、前回のエージェント回答より新しいHumanのコメント、changes requested、質問、または失敗したCIがある場合は、他の作業より先に対応する。

- 指摘内容と関連コードを確認し、正しい修正かを判断する。
- 判断に必要な情報が不足している場合は、推奨案、代替案、各案の影響をPRにコメントし、質問して終了する。
- 修正する場合は既存PRのbranchを使用する。新しいPRを作らない。
- 関連テスト、lint、型検査等を実行し、diffをセルフレビューする。
- commit、pushしてPRを更新し、変更内容と検証結果をコメントする。
- 新しいcommitをpushした場合、以前のPR承認は無効と考え、Humanの再確認を待つ。
- 同じコメントへ既に回答済みで、head commitも変わっていない場合は重複して対応しない。

対応後は終了する。

### 2. open PRがHuman確認またはmergeを待っている

未対応フィードバックがないopen PRがある場合、新しいIssueやPRを作らない。

- 最新head commitへのApproveがない場合は、`AWAITING_PR_REVIEW` として終了する。
- 最新head commitがApprove済みで未mergeの場合は、`AWAITING_HUMAN_MERGE` として終了する。
- merge済みの場合は関連Issueの状態を確認し、次の工程へ進む。

### 3. 承認済みIssueを実装する

Human承認済みで、対応するopen PRが存在しないIssueがある場合、そのIssueを1つ選択して実装する。

実装前に次を再確認する。

- 現在のリポジトリと `GOAL.md` の差分に照らして、Issueが引き続き妥当である。
- Issueの目的、対象範囲、対象外、完了条件が実装可能な程度に明確である。
- 承認後に内容が実質的に変更されていない。
- 他のopen PRやIssueと重複せず、実施順序に問題がない。

問題がある場合は実装せず、理由と修正案をIssueにコメントしてHumanの再確認を待つ。

問題がない場合は次のように実装する。

1. `origin/main` の最新commitから新規branchを作成する。
2. Issueの範囲内だけを変更する。
3. 必要なテストを追加または更新する。
4. 関連テスト、lint、型検査等を実行する。
5. Issueの完了条件、既存実装との整合性、不要な変更、回帰リスクについてdiffをセルフレビューする。
6. commit、pushし、PRを作成する。

PRには以下を記載する。

- 関連Issue
- 変更内容
- `GOAL.md` のゴールとの関係
- 実行した検証と結果
- 未検証事項と既知のリスク
- Humanに判断してほしい点

PR本文では `Closes #<Issue番号>` を使用し、Humanによるmerge時にIssueが閉じるようにする。PR作成後は `AWAITING_PR_REVIEW` として終了する。

### 4. 未承認IssueにHumanの新しいコメントがある

エージェントが作成した未承認Issueに、前回のエージェント回答より新しいHumanの質問または修正依頼がある場合は対応する。

- 質問には、専門用語を必要に応じて説明し、Issueの判断に必要な範囲で回答する。
- 修正依頼が妥当ならIssue本文を更新し、変更点をコメントする。
- 目的、スコープ、完了条件を変更した場合は、あらためて `/approve-issue` を依頼する。
- 情報不足で一意に修正できない場合は、推奨案、代替案、各案の影響を示して質問する。
- 同じコメントへ既に回答済みなら重複して投稿しない。

対応後は終了する。

### 5. IssueがHuman確認を待っている

未承認の提案Issueがあり、新しいHumanコメントがない場合は、新しいIssueを作らず `AWAITING_ISSUE_APPROVAL` として終了する。

### 6. 次のIssueを1件提案する

対応すべきopen PR、承認済みIssue、未承認の提案Issueがない場合だけ、新しいIssueを1件作成する。

Issueを作成する前に、現在のリポジトリから `GOAL.md` のゴールへ進むために必要な作業を複数検討し、次の基準で最も優先すべき1件を選ぶ。

- ゴールとの差分を直接縮めるか
- 現時点で実施可能か
- 後続作業の前提またはボトルネックか
- 既存Issue、PR、実装と重複しないか
- 1つのPRでレビュー可能な粒度か
- 完了を客観的に検証できるか

Issue作成前に、別工程としてコメントを投稿するのではなく、提案内容そのものをセルフレビューする。

- やることと、やらないことが明確か
- 完了条件と検証方法が明確か
- 不要な作業や過剰な一般化がないか
- 現在の順序で実施する理由を説明できるか

Issueには以下を記載する。

- 背景と現在の状態
- `GOAL.md` との差分
- 目的
- 対象範囲
- 対象外
- 推奨する実装方針
- 完了条件
- 検証方法
- 判断が必要な点、代替案、その影響
- 実装承認方法として `/approve-issue` を使用すること

Issue作成後は実装せず、`AWAITING_ISSUE_APPROVAL` として終了する。

## WIPと重複防止

- エージェントが作成したopen PRは同時に最大1件とする。
- Human承認待ちの提案Issueは同時に最大1件とする。
- 既存のIssue、PR、branch、コメントを検索してから作成または投稿する。
- 同じ入力状態に対して、Issue、PR、コメント、branchを重複作成しない。
- 待機状態ではGitHubやファイルを変更しない。

## 権限境界

エージェントが自律的に実行できるのは、Issueの作成・更新・コメント、承認済みIssueの実装、branchの作成、commit、push、PRの作成・更新までとする。

次の操作は行わない。

- PRのmerge
- `main` への直接push
- 有料リソースの作成または起動
- 購入、課金契約、本番環境の変更
- secretやcredentialの作成、変更、表示
- 既存作業を失う可能性がある破壊的操作

費用や外部リソースが必要な場合は、推奨案、代替案、使用するリソース、概算費用、費用上限、停止条件をIssueまたはPRに提示し、Humanの明示承認を待つ。Issueの実装承認だけを、費用発生の承認として扱わない。

## 実行結果

終了時に、次のいずれかの状態と要約を出力する。

- `CREATED_ISSUE`
- `UPDATED_ISSUE`
- `AWAITING_ISSUE_APPROVAL`
- `CREATED_PR`
- `UPDATED_PR`
- `AWAITING_PR_REVIEW`
- `AWAITING_HUMAN_MERGE`
- `BLOCKED`
- `NO_WORK`

要約には、対象IssueまたはPR、実行した変更、検証結果、GitHub上で行った操作、次に必要なHuman操作または停止理由を含める。
